## 1. Part 1 — 클라우드 컴퓨팅과 NCP 개요

### 클라우드 컴퓨팅

서버, 스토리지, 네트워크, 데이터베이스 같은 인프라부터 관리형 DB·데이터 분석·AI·개발 도구까지 IT 자원을 **인터넷으로 필요할 때 빌려 쓰고, 쓴 만큼만 비용을 내는 방식**이다. 온디맨드로 몇 분 만에 생성할 수 있고 종량 과금이 적용된다.

| 비교 | 온프레미스(직접 구축) | 클라우드 |
| --- | --- | --- |
| 비유 | 집을 직접 사서 사는 것 | 호텔·공유 오피스를 빌리는 것 |
| 준비 기간 | 장비 주문·설치까지 수주~수개월 | 클릭 몇 번, 수 분 |
| 초기 비용 | 서버 구입비 큼(선투자) | 없음(쓴 만큼 후불) |
| 정리 | 장비가 그대로 남음 | 반납하면 비용도 멈춤 |

장점:

- **CAPEX를 OPEX로 대체** — 데이터센터·장비를 미리 사지 않고 필요한 시점에 사용한 만큼 지불
- **규모의 경제** — 대규모로 준비된 인프라의 이점이 고객 혜택으로 돌아옴
- **지속적인 기술 혁신** — 사업자가 새 서비스를 계속 제공
- **빠른 프로비저닝과 유연한 확장** — 몇 분 만에 서버 확보, 필요할 때 확장
- **인프라 유지 관리 부담 제거** — 사업의 핵심에 집중

### 서비스 모델

관리 책임의 범위로 구분한다.

| 모델 | 설명 | 사용자가 주로 관리하는 것 |
| --- | --- | --- |
| IaaS | 컴퓨팅·네트워크·스토리지 등 인프라를 서비스로 사용 | OS와 애플리케이션 |
| CaaS | OS가 아닌 컨테이너 레벨 기능을 서비스로 사용 | 컨테이너 이미지와 워크로드 |
| PaaS / aPaaS | 인프라를 직접 관리하지 않고 플랫폼 소프트웨어를 사용 | 애플리케이션과 데이터 |
| FaaS | 서버가 아닌 함수(function code) 단위로 실행 | 함수 코드와 실행 설정 |
| SaaS | 완제품 소프트웨어를 서비스로 사용 | 사용과 설정 |

> 오늘 실습은 **IaaS 방식**: 서버만 빌리고, 그 위의 Ubuntu 설정·웹서버 설치·웹페이지 배포는 직접 한다.

### NAVER Cloud Platform(NCP)

- NAVER와 LINE 서비스에 쓰인 것과 동일한 기술·인프라로 구현된 퍼블릭 클라우드
- Clova, Papago 등 네이버 AI 기술을 클라우드 상품(API)으로 제공
- KISA 클라우드 서비스 보안 인증(CSAP), ISMS, CSA STAR 등 보안 인증 보유. 공공·금융·민간 컴플라이언스에 맞춘 클라우드 제공
- 연혁: 2012년 Ncloud v1.0 자체 개발 → 2017년 4월 NCP 출시, 같은 해 공공 클라우드 출시 → 2019년 국내 최초 금융 클라우드 출시

### 상품군 개요

| 상품군 | 대표 서비스 | 특징 |
| --- | --- | --- |
| Server(인프라) | Server, VDS, GPU Server, Bare Metal Server | 웹 콘솔에서 수 분 내 생성, 이미지 선택으로 OS 설치 불필요, 스펙 변경·기본 모니터링, 추가 Block Storage(HDD/SSD) 연결 |
| Network(인프라) | VPC, Subnet, Load Balancer, Global DNS, CDN | VPC에서는 원하는 사설 IP 대역(RFC1918)으로 논리적 사설망 구축. 서버는 반드시 Subnet 안에 생성 |
| Database(플랫폼) | Cloud DB for MySQL·MS-SQL·Redis 등 관리형, 설치형 DB | 관리형은 이중화·자동 Fail-over·자동 백업·스토리지 자동 증가 제공 |
| AI Service(애플리케이션) | CLOVA Speech, Papago NMT, Chatbot 등 | 네이버 데이터로 학습된 AI를 API 형태로 사용 |

- **VPC 플랫폼과 Classic 플랫폼은 네트워크 환경과 서버 사양이 완전히 다르다.** Classic은 서버 생성 시 사설 IP를 랜덤 부여받는 구형 환경이다. 오늘 실습은 **VPC 플랫폼** 기준이다.
- **리전과 Zone**: 전 세계 주요 거점에 리전을 운영하며, 한국·싱가포르 리전 등에서 멀티 존 구성(로드밸런서 이중화, 백업·DR)이 가능하다. 강의 자료 기준 VPC 환경은 일부 리전에서만 제공되므로 실습은 **Korea 리전**으로 한다.
- **하이브리드 클라우드 호스팅**: 규제·정책상 클라우드 활용에 제약이 있으면 데이터센터 환경의 물리 장비 임대와 클라우드를 함께 사용할 수 있다.

## 2. 실습 전 필수 개념 브리핑

### IP 주소 — 컴퓨터의 "집 주소"

| 구분 | 공인 IP(Public IP) | 사설 IP(Private IP) |
| --- | --- | --- |
| 비유 | 아파트의 도로명 주소 | 아파트 안의 동·호수 |
| 사용 범위 | 전 세계 인터넷 어디서나 접근 | 같은 내부망(VPC) 안에서만 |
| 예시 | `118.67.130.25` | `10.0.1.6` |
| 오늘 실습 | 브라우저·SSH 접속에 사용 | 서버 생성 시 자동 부여 |

**CIDR**은 네트워크 주소와 prefix 길이로 주소 범위를 표현한다.

| 표기 | 범위 | IP 개수 | 오늘 용도 |
| --- | --- | --- | --- |
| `10.0.0.0/16` | 10.0.0.0 ~ 10.0.255.255 | 65,536 | VPC 전체 |
| `10.0.1.0/24` | 10.0.1.0 ~ 10.0.1.255 | 256 | Public Subnet |
| `0.0.0.0/0` | 모든 IP(전체 인터넷) | 전체 | ACG 접근 소스 |

### VPC와 Subnet — 아파트 단지와 동

- **VPC** = 담장으로 둘러싸인 아파트 단지(나만의 격리된 가상 네트워크)
- **Subnet** = 단지 안의 동(棟), **서버** = 동 안의 세대(집)

| 구분 | Public Subnet | Private Subnet |
| --- | --- | --- |
| 인터넷 | 공인 IP 연결 가능 | 외부 직접 접근 불가 |
| 용도 | 웹서버 | DB 등 내부 서버 |

실습 예시 주소 설계:

| 리소스 | 이름 | 주소 범위 | 용도 |
| --- | --- | --- | --- |
| VPC | `yau-vpc-01` | `10.0.0.0/16` | 실습 사설망 |
| Public Subnet | `yau-pub-sub-01` | `10.0.1.0/24` | 웹 서버 |
| Private Subnet | `yau-pri-sub-01` | `10.0.2.0/24` | 내부 서비스·DB 예시 |

> 가장 많이 하는 실수: 웹서버를 **Private Subnet**에 만들면 공인 IP를 연결할 수 없어 브라우저로 접속할 수 없다.

### 방화벽(ACG)과 포트 — 현관문과 출입문 번호

- **NACL**: Subnet 전체에 적용(아파트 동 출입구 경비). 오늘은 기본값 사용
- **ACG(Access Control Group)**: 서버 NIC에 적용(각 세대 현관문 도어락). 허용한 프로토콜·출발지 CIDR·포트만 통과
- **포트**: IP가 건물 주소라면 포트는 건물의 출입문 번호

| 포트 | 프로토콜 | 용도 | 오늘 ACG |
| --- | --- | --- | --- |
| 22 | SSH | 터미널로 서버에 원격 접속 | 허용 |
| 80 | HTTP | 브라우저로 웹페이지 보기 | 허용 |
| 443 | HTTPS | 암호화된 웹(인증서 필요) | 이후 과정 |

"브라우저 접속이 안 돼요!"의 대부분은 ACG에 80번 포트를 열지 않아서다.

### 서버 생성 시 정하는 6가지와 상태 흐름

| 순서 | 항목 | 의미 | 오늘 실습 값 |
| --- | --- | --- | --- |
| 1 | 서버 이미지 | 설치할 OS | Ubuntu Server 22.04 LTS |
| 2 | 서버 스펙 | CPU·메모리 | vCPU 2개 / 메모리 4GB |
| 3 | VPC · Subnet | 서버 위치(단지·동) | `yau-vpc-01` / `yau-pub-sub-01` |
| 4 | 서버 이름 | 콘솔 표시 이름 | `yau-web-svr-01` |
| 5 | 인증키 | 비밀번호를 여는 열쇠 파일 | `yau-key-01.pem` |
| 6 | ACG | 방화벽 | `yau-web-acg` |

- 생성: 생성중 → 부팅중 → 설정중 → **운영중**(접속 가능, 약 5~10분)
- 정지: 운영중 → 종료중 → 정지
- 반납: 정지 → 완전 삭제(복구 불가). **오늘 만든 서버는 Day 2 실습 종료 전까지 반납 금지**

### 인증키(.pem) · root 비밀번호 · SSH

① 서버 생성 시 `yau-key-01.pem` 다운로드 → ② 콘솔 [관리자 비밀번호 확인]에 `.pem` 업로드 → root 비밀번호 표시 → ③ `ssh root@<공인 IP>` + root 비밀번호로 접속

- 접속 성공 시 프롬프트 `root@yau-web-svr-01:~#` — "이제 서버 안에 있다"
- 비밀번호 입력 시 화면에 아무것도 표시되지 않는 것이 정상
- Mac은 터미널, Windows 10·11은 PowerShell(ssh 기본 내장)
- `.pem` 파일은 한 번만 다운로드 가능하고, root 비밀번호는 Day 2에서도 사용 → 기록 카드에 저장하고 공유 금지

### 웹페이지가 보이는 원리와 꼭 기억할 경로

브라우저 `http://<공인 IP>` → 80번 포트 → ACG(80 허용?) → Nginx가 `/var/www/html/`에서 `index.html`을 찾음 → 브라우저가 화면을 그림. 주소 뒤에 파일 이름이 없으면 웹서버는 기본으로 `index.html`을 보내준다.

| 경로 | 설명 | Day 2 |
| --- | --- | --- |
| `/var/www/html/` | 웹 파일을 두는 웹 루트 폴더 | |
| `/var/www/html/index.html` | 브라우저 접속 시 보이는 메인 페이지 | 수정·재배포 |
| `/var/www/html/index_day1.html` | Day 1 결과 백업본 | 비교·복원 |
| `/etc/nginx/` | Nginx 설정 폴더(오늘은 수정하지 않음) | |
| `/var/log/nginx/access.log` | 접속 로그 | |

백업 = 바꾸기 전에 복사본 남기기: `cp index.html index_day1.html`

### 오늘 사용할 리눅스 명령어

| 명령어 | 뜻 | 예시 |
| --- | --- | --- |
| `pwd` / `ls -l` | 현재 위치 / 파일 목록 | `ls -l /var/www/html` |
| `cd` | 폴더 이동 | `cd /var/www/html` |
| `cat` | 파일 내용 보기 | `cat index.html` |
| `cp` | 파일 복사(백업) | `cp index.html index_day1.html` |
| `nano` | 간단한 텍스트 편집기 | `nano index.html` |
| `apt-get` | 프로그램 설치 | `apt-get install -y nginx` |
| `systemctl` | 서비스 시작·상태 확인 | `systemctl status nginx` |
| `exit` | 서버 접속 종료 | `exit` |

명령어는 외우지 않아도 된다. 실습 자료에서 복사해 터미널에 붙여넣으면 된다.

### 비용·보안 수칙

- 서버·공인 IP는 반납 전까지 시간당 요금이 발생한다. 오늘 만든 서버·공인 IP는 Day 2에서 계속 사용하고 Day 2 종료 후 반납한다.
- 크레딧 잔액은 포털 [마이페이지]에서 수시로 확인한다.
- `.pem`, root 비밀번호, Secret Key는 공유하거나 GitHub에 올리지 않는다.
- 필요한 포트(22, 80)만 개방한다.

## 3. Part 2 — 계정 생성 및 이용 환경 준비

- NCP **계정**은 등록한 이메일 주소이며, 개인 정보와 결제 정보를 가지고 모든 서비스를 이용할 수 있다.
- 회원 가입: 포털(`www.ncloud.com`) [회원가입] → 이메일로 가입 → 거주 국가·회원 유형·사용 언어 선택 → 약관 동의 → 로그인 정보·이메일 인증 → 본인 명의 휴대폰 SMS 실명 인증
  - **거주 국가는 결제 통화를 결정하며 가입 후 변경 불가**하므로 신중히 선택한다.
  - 학생은 개인 회원으로 가입한다(이후 사업자 전환 가능).
- 결제 수단 등록: [마이페이지] > [결제 관리] > [결제 수단 관리]. 유효성 검증을 위해 0원 또는 1,000원 결제 후 즉시 취소된다. 결제 수단이 등록돼야 서버·VPC 등 리소스를 만들 수 있다.
- 사업자 전환(선택): [마이페이지] > [계정 관리]에서 사업자등록증 등을 제출한다.
- 크레딧 등록: [마이페이지] > [크레딧 관리] > [크레딧 등록]에서 강의용 프로모션 코드 입력 → 실습 비용이 자동 차감된다.

## 4. Part 3 — 서브 계정(Sub Account)

Sub Account는 주 계정 정보를 공유하지 않고 여러 담당자가 자원을 함께 운영하도록 **서브 계정에 상세 권한을 부여하는 IAM 서비스**다.

- **최소 권한의 원칙**: 허용된 권한 범위 안에서만 자원 관리
- 이메일·SMS·패스키·OTP 기반 **2차 인증(MFA)** 강제
- 콘솔·API에 접근 가능한 **IP 대역 제한**으로 비인가 접근 차단
- 서브 계정별 활동 로그로 보안 감사 가능

| 구성 | 설명 |
| --- | --- |
| 서브 계정 생성 | [Services] > [Management & Governance] > [Sub Account]. 로그인 타입은 Console 접근(웹 GUI) 또는 API 접근(CLI·SDK·자동화) |
| 정책(Policy) | 관리형 정책(예: `NCP_INFRA_MANAGER`, `NCP_VPC_SERVER_MANAGER`, `NCP_VIEWER`) 또는 사용자 정의 정책. 규칙은 Effect(Allow/Deny) · Action(예: `Server:Get*`) · Resource |
| 역할(Role) | 사람이 아닌 서버 인스턴스나 외부 서비스에 임시 자격 증명을 부여 |
| 전용 로그인 URL | 서브 계정은 일반 포털이 아닌 전용 로그인 주소로 접속 |
| 보안 설정 | 접근 IP 대역, 비밀번호 만료 주기·복잡도, MFA |

API 자동화에는 인증 키(Access Key/Secret Key)를 사용한다. 키나 비밀번호를 코드, 공개 저장소, 공유 문서에 넣지 않는다.

## 6. Part 6 — 서버(Compute)와 가상 머신 기초

### 가상화

- **하이퍼바이저**: 하드웨어와 VM 사이에서 VM과 하드웨어를 관리하는 가상화 소프트웨어
- **전가상화**: 하드웨어 전체를 가상화. VM은 일반 OS를 그대로 쓸 수 있지만 오버헤드가 있음
- **반가상화**: 하이퍼콜로 직접 요청해 성능 저하를 줄임. VM의 OS가 이를 지원해야 함

### 서버 특징

| 자원 | 특징 |
| --- | --- |
| 세대 | G1·G2로 구분. 강의 자료 기준 VPC의 일반 서버는 G2 제공 |
| CPU | vCPU 단위 할당, OverCommit 허용, 스펙 변경 가능 |
| Memory | GB 단위 할당, OverCommit 허용 안 함, 스펙 변경 가능 |
| 디스크 | OS 영역 기본 할당(Linux 50GB, Windows 100GB), OS 영역은 확장·축소 불가. SSD/HDD |
| Network | 물리 10Gbps, 논리 1Gbps |

서버 타입(VPC):

| 타입 | CPU:Memory | 용도 |
| --- | --- | --- |
| High CPU | 1:2 | 연산 집약적 워크로드 |
| **Standard** | 1:4 | 일반적인 서버(오늘 실습) |
| High Memory | 1:8 | 대용량 메모리가 필요한 경우 |

기타 서버 상품:

- **VDS(Virtual Dedicated Server)**: 물리 서버 하나에 VM 하나만 생성되어 OverCommit이 없음
- **Bare Metal Server**: 하이퍼바이저 없이 하드웨어 자원을 그대로 사용. 라이선스상 클라우드 제약이 있을 때 사용
- **GPU Server**: GPU를 PassThrough 방식으로 제공
- **Preinstall Image**: DBMS·애플리케이션이 미리 설치된 이미지

### 서버 운영 기능

| 기능 | 설명 |
| --- | --- |
| 스펙 변경 | 같은 서버 타입 안에서 CPU·메모리 변경(정지 상태). 다른 타입으로 바꾸려면 내 서버 이미지로 새 서버 생성 |
| 내 서버 이미지 | 서버의 현재 상태를 이미지로 생성. 리전 간 복제, 마스터 이미지에 활용 |
| 유사 서버 생성 | 선택한 서버와 같은 이미지·스펙·인증키·ACG로 생성 |
| 추가 스토리지 | 10GB ~ 2TB, 서버당 최대 15개 추가. 용량 증설 가능 |
| 스냅샷 | 스토리지 단위 백업. OS 영역 장애 시 데이터 복구에 활용 |
| 반납 보호 | 실수로 반납되지 않도록 설정 |
| Init Script | 서버 생성 시 1회만 실행하는 초기화 스크립트 |
| 인증키 변경 | 인증키 분실 시 초기 비밀번호 확인을 위해 변경 |

- 기본 원칙: 애플리케이션은 OS 영역에, 데이터는 추가 스토리지에 두어 장애 시 유실을 줄이고 빠르게 복구한다.
- **공인 IP**: 서버에 종속되지 않고 서버에 매핑하는 자원이다. VPC 환경에서는 리전에 종속되어 Zone 구분 없이 사용한다. 외부 접속은 공인 IP 또는 VPN으로 한다.
- **ACG**: TCP·UDP·ICMP와 접근 소스(CIDR 또는 ACG)를 지정한다. VPC에서는 서버 NIC에 적용되고 Inbound/Outbound 규칙을 가진다.

## 7. Part 7 — 클라우드 스토리지 기초

스토리지는 서버를 다시 시작해도 파일과 데이터를 보존하는 저장 공간이다.

| 구분 | Block Storage | Object Storage |
| --- | --- | --- |
| 저장 방식 | 서버에 볼륨으로 연결하고 OS에서 파일 시스템을 만들어 사용 | 버킷에 객체(파일 + 메타데이터)를 저장하고 업로드·다운로드 |
| 주된 용도 | 서버의 OS, 애플리케이션, 웹서버 파일, 작업 데이터 | 이미지, 문서, 백업 파일, 정적 웹 자원 |
| Day 1 예 | Ubuntu 서버 기본 디스크와 `/var/www/html/index.html` | 선택 실습에서 HTML 파일을 버킷에 올려 정적 웹 호스팅 |

서버에 붙여 OS와 함께 쓰는 디스크가 필요하면 Block Storage, 파일을 버킷 단위로 보관·제공하려면 Object Storage를 선택한다.

> 서버를 **정지**해도 디스크 등 리소스 비용이 남을 수 있다. 완전히 비용을 멈추려면 반납해야 한다.

## 8. 핵심 요약

Day 1의 핵심 흐름은 **VPC/Subnet 설계 → ACG로 필요한 포트 허용 → Public Subnet의 Ubuntu 서버 생성 → 공인 IP와 SSH 연결 → Nginx 설치 → 웹 페이지 배포 및 백업**이다. 네트워크 공개 범위와 인증정보 보관을 신중히 하고, Day 2에 필요한 서버·공인 IP는 지정된 시점까지 유지한다.

| 키워드 | 한 줄 정리 |
| --- | --- |
| 클라우드 | IT 자원을 빌려 쓰고 쓴 만큼 내는 방식, 오늘은 IaaS |
| VPC / Subnet | 격리된 사설망 / 그 안을 용도별로 나눈 망. 웹서버는 Public Subnet |
| ACG | 서버 방화벽. 22(SSH)·80(HTTP)만 허용 |
| 공인 IP | 인터넷에서 서버를 찾는 주소. 서버에 연결하는 별도 자원 |
| SSH | `ssh root@<공인 IP>`로 암호화된 원격 접속 |
| 웹 루트 | `/var/www/html/index.html`이 첫 화면 |
| 스토리지 | 서버 디스크는 Block, 버킷 파일 보관은 Object |
