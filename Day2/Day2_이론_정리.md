## 1. Day 1 복습

Day 1에는 NCP에 VPC/Subnet을 만들고, Ubuntu 서버에 웹서버(Nginx)를 설치해 예제 `index.html`을 브라우저로 확인했다.

```
[내 노트북] → 인터넷 → [NCP VPC > Subnet > Ubuntu Server > 웹서버 > /var/www/html/index.html]
브라우저에서 http://<공인 IP> → index.html 표시
```

**오늘의 최종 목표는 이 `index.html`을 AI와 함께 만든 나만의 웹사이트로 교체하는 것**이다.

| 용어 | 한 줄 설명 | 오늘 쓰는 곳 |
| --- | --- | --- |
| 공인 IP | 인터넷에서 내 서버를 찾는 주소 | 브라우저 접속 · 원격 접속 주소 |
| root 비밀번호 | 서버 관리자 계정 비밀번호(인증키 `.pem`으로 확인) | VS Code · MobaXterm · 터미널 로그인 |
| ACG | 서버 방화벽, 허용한 포트만 통과 | 22번(SSH) · 80번(HTTP) |
| 웹서버(Nginx) | 브라우저 요청에 웹 파일을 보내주는 프로그램 | 배포한 파일을 보여 줌 |
| 문서 루트 | 웹 파일을 두는 폴더 `/var/www/html` | `index.html` 교체 위치 |

## 2. Part 1 — Agentic AI란 무엇인가

### LLM(대규모 언어 모델)

방대한 글을 학습해 **"다음에 올 가장 자연스러운 말"을 이어 만드는 AI**다. 코드도 일종의 언어이므로 프로그램도 작성할 수 있다. Claude · ChatGPT · Gemini 모두 LLM을 두뇌로 쓰는 서비스다.

동작 흐름: **① 입력(프롬프트) → ② 이해(요청·이전 대화·첨부 자료로 문맥 파악) → ③ 생성(토큰을 하나씩 예측) → ④ 출력(설명·코드·표·요약)**

| 잘하는 것 | 조심할 것 |
| --- | --- |
| 글·코드 초안을 빠르게 작성 | 그럴듯한 오답(**환각, Hallucination**)을 자신 있게 말함 |
| 긴 문서 요약·번역·정리 | 학습 이후의 최신 정보는 모를 수 있음 |
| 예시를 보고 형식 맞추기 | 대화가 너무 길면 앞부분을 놓칠 수 있음 |
| 설명을 쉬운 말로 바꾸기 | 챗봇 방식에서는 내 서버·파일 상황을 직접 보지 못함 |

**결론: AI의 답은 "검토할 초안"이다.** 코드는 실행해서 확인하고, 사실은 공식 자료로 확인한다.

### 컨텍스트(Context) — AI의 "작업 기억"

AI가 답을 만들 때 참고하는 **지금까지의 대화 + 첨부 자료 전체**. 같은 대화 안에서 앞의 조건(예: "파란색 계열")을 기억하는 이유다.

| 상황 | 일어나는 일 | 대처 |
| --- | --- | --- |
| 같은 대화에서 계속 수정 | 이전 요청을 기억하며 수정 | 그대로 이어서 요청 |
| 대화가 너무 길어짐 | 앞 조건을 놓치거나 느려짐 | **최종 코드만 새 채팅에 붙여넣고** 이어 가기 |
| 새 채팅 시작 | 이전 대화를 모름 | 필요한 조건·코드를 다시 알려 주기 |

### AI 활용 방식의 변화: 챗봇 → 코파일럿 → 에이전트

| 단계 | 방식 | 사람의 역할 | 비유 | 코딩에서는 |
| --- | --- | --- | --- | --- |
| 1. 챗봇 | 질문하면 답변 | 매번 묻고 결과를 직접 적용 | 길 물어보기 | 코드를 받아 사람이 복사·붙여넣기·실행 |
| 2. 코파일럿 | 옆에서 제안 | 제안을 보고 수락/거절 | 내비게이션 | 코드를 치는 동안 다음 줄을 제안 |
| 3. 에이전트 | 목표를 주면 스스로 계획·실행 | 목표 설정과 결과 검토 | 자율주행 | 파일 수정·명령 실행·오류 수정까지 스스로 |

AI가 "대답하는 도구"에서 "일을 해내는 동료"로 바뀌고 있다. **오늘은 1단계(챗봇) 방식**으로 Claude와 협업하고, 이후 과정에서 3단계(에이전트)를 직접 체험한다.

### Agentic AI의 정의와 에이전트 루프

> **목표를 받으면 스스로 계획을 세우고, 도구를 사용해 실행하고, 결과를 확인하며 목표를 달성할 때까지 반복하는 AI**

**목표 → 계획 → 실행 → 관찰 → (수정 → 다시 계획) 반복**

예시 — 목표: "내 웹사이트에 다크모드 버튼을 추가하고 서버에 반영해 줘"

| 단계 | 에이전트가 하는 일 |
| --- | --- |
| 계획 | ① `index.html` 구조 확인 ② 버튼·CSS·JS 추가 ③ 브라우저 확인 ④ 서버 반영 |
| 실행 | `index.html`에 버튼과 다크모드 스타일·스크립트 추가 |
| 관찰 | 버튼은 보이지만 글자색이 안 바뀜 |
| 수정 | 원인 분석 → CSS 선택자 수정 → 다시 실행 |
| 관찰 | 정상 동작 확인 |
| 완료 보고 | "다크모드 버튼 추가 완료, 변경 파일: index.html" |

핵심은 **"관찰 → 수정"의 반복**이다. 사람이 매번 알려 주지 않아도 결과를 보고 스스로 고친다.

### 에이전트의 4가지 구성 요소

| 구성 요소 | 역할 | 비유 |
| --- | --- | --- |
| LLM | 판단하고 생각 | 두뇌 |
| 도구(Tools) | 파일 작성, 명령 실행, 검색 등 | 손과 발 |
| 컨텍스트/메모리 | 지금까지의 작업 내용 기억 | 작업 노트 |
| 계획(Planning) | 큰 목표를 작은 단계로 분해 | 할 일 목록 |

LLM은 원래 글만 만드는 두뇌인데, **도구를 연결하면 실제로 행동**할 수 있다(파일 읽기·쓰기, 터미널 명령, 웹 검색, 메일·일정·문서 등 외부 서비스).
동작: LLM이 도구 사용 요청 → 도구 실행 → 결과 전달 → LLM이 결과를 보고 다음 행동 결정.

> **MCP(Model Context Protocol)**: AI와 여러 도구·서비스를 연결하는 공개 표준 규격. "AI용 USB 포트"에 비유한다.

### 챗봇 vs 에이전트 (같은 요청, 다른 결과)

| | 챗봇 | 에이전트 |
| --- | --- | --- |
| 하는 일 | 코드를 알려 줌 | 파일을 직접 수정 |
| 적용 | 사람이 복사·붙여넣기 | 스스로 저장 |
| 확인 | 사람이 테스트 | 실행하고 오류를 스스로 수정 |
| 배포 | 사람이 업로드 | 명령을 실행해 반영 |

활용 분야: 소프트웨어 개발(기능 추가·버그 수정·테스트·리뷰), 인프라 운영(상태 점검·로그 분석·설정 변경), 데이터 분석, 업무 자동화, 리서치.

### 에이전트 시대, 사람의 역할

1. **목표 정하기** — 무엇을·왜·어느 수준까지 만들지 명확히 전달
2. **권한 관리** — AI가 어디까지 할 수 있는지 정하고, 위험한 작업은 승인
3. **결과 검증** — 화면·동작·보안을 직접 확인
4. **책임지기** — 배포한 결과의 최종 책임은 사람

> 에이전트의 위험: 잘못된 명령 실행, 중요 파일 삭제, 비밀 정보 노출. 그래서 **사람의 승인(Human-in-the-loop)과 백업이 필수**다.

### 고르는 기준: "어느 것이 최고인가"보다 "무엇에 쓰는가"

| 관점 | 확인할 질문 |

3대장의 특징(강의 요약):

> 실무 팁: 하나만 고집하기보다 **같은 질문을 2~3곳에 물어 비교**하면 더 좋은 답을 얻는다.

활동 — 같은 프롬프트(예: "영남대 학생 동아리 소개 웹페이지를 index.html 한 파일로…")를 여러 AI에 넣고 **요청 섹션 포함 여부 · 바로 실행되는 코드인지 · 디자인 완성도 · 설명의 이해 용이성**으로 비교한다.

**이 과정에서 Claude를 쓰는 이유**: ① 완성된 코드 결과물(웹사이트) 생성에 강함 ② 채팅 화면에서 바로 미리 보기하며 수정 가능 ③ 이후 배울 코딩 에이전트까지 하나의 흐름(대화 → 바이브 코딩 → 에이전트)으로 연결됨.

## 4. Part 3 — 바이브 코딩

### 바이브 코딩(Vibe Coding)이란

코드를 한 줄씩 직접 쓰는 대신 **원하는 결과를 말로 설명하고, AI가 만든 코드를 보며 다듬어 가는 개발 방식**. 2025년 초 안드레 카파시(Andrej Karpathy)가 처음 쓴 표현으로, "무엇을 만들지"에 집중하고 "어떻게 짤지"는 AI에게 맡긴다.

| 비교 | 전통적인 개발 | 바이브 코딩 |
| --- | --- | --- |
| 시작 | 문법·언어를 먼저 배움 | 만들고 싶은 결과를 먼저 말함 |
| 코드 작성 | 사람이 한 줄씩 직접 | AI가 작성, 사람은 설명·요청 |
| 수정 | 코드를 직접 찾아 고침 | "이 부분을 이렇게 바꿔 줘"라고 요청 |
| 필요한 능력 | 문법·디버깅 지식 | 기획력·설명력·검증 습관 |
| 강점 | 세밀한 제어, 깊은 이해 | 빠른 결과, 아이디어 검증 |

**흐름**: ① 아이디어 → ② 프롬프트 → ③ AI 코드 생성 → ④ 미리 보기·확인 → ⑤ 만족? (아니오면 수정 요청 후 ③으로) → ⑥ 배포

핵심은 **한 번에 완벽하게 만들려 하지 않는 것**. 작게 만들고, 보고, 고치기를 반복한다.

### 웹페이지를 이루는 3가지

| 구성 | 역할 | 비유 | 위치 | 이런 요청이면 여기 |
| --- | --- | --- | --- | --- |
| HTML | 무엇이 있는가(내용·구조: 제목, 문단, 버튼, 메뉴) | 뼈대 | `<h1>`, `<p>`, `<section>` | "프로젝트 섹션을 하나 더" |
| CSS | 어떻게 보이는가(색·글꼴·여백·배치·모바일 대응) | 옷 | `<style>` 안 | "제목을 더 크게, 파란색으로" |
| JavaScript | 무엇을 하는가(클릭·다크모드 전환·애니메이션) | 동작 | `<script>` 안 | "버튼을 누르면 다크모드로" |

### `index.html` 한 파일의 구조

```html
<!DOCTYPE html>
<html lang="ko">
<head>
  <meta charset="UTF-8">                                                  <!-- 한글 깨짐 방지 -->
  <meta name="viewport" content="width=device-width, initial-scale=1.0"> <!-- 모바일 대응 -->
  <title>홍길동의 홈페이지</title>                                         <!-- 브라우저 탭 제목 -->
  <style>/* CSS: 색 · 글꼴 · 배치 */</style>
</head>
<body>
  <header> ... </header>                      <!-- HTML: 화면에 보이는 내용 -->
  <section id="projects"> ... </section>
  <script>/* JavaScript: 버튼 · 애니메이션 */</script>
</body>
</html>
```

프롬프트에서 **"index.html 하나에 CSS와 JavaScript 포함"을 요구하는 이유**: 파일 하나만 서버에 올리면 배포가 끝나기 때문이다.

### 장점과 함정

| 장점 | 함정 |
| --- | --- |
| 코딩 경험이 적어도 결과물을 만들 수 있음 | 코드를 이해하지 못한 채 배포 |
| 아이디어를 빠르게 확인 | 오류가 나면 원인을 모름 |
| 반복 수정이 빠름 | 개인정보·비밀번호를 코드에 넣는 실수 |

> 원칙: **AI가 만든 코드도 내가 책임지는 코드**다. 모르는 부분은 "이 코드가 무슨 일을 하는지 설명해 줘"라고 묻는다.

### 좋은 프롬프트의 4요소

| 요소 | 예시 |
| --- | --- |
| 목표 | 나를 소개하는 개인 홈페이지를 만들어 줘 |
| 내용 | 이름, 학과, 관심 분야, 프로젝트 3개 |
| 조건 | HTML 파일 1개, CSS·JS는 파일 안에 포함, 한글 |
| 스타일 | 깔끔한 카드형 디자인, 파란색 계열, 모바일 대응 |

### 프롬프트를 더 잘 쓰는 4가지 기법

| 기법 | 방법 | 예시 |
| --- | --- | --- |
| 역할 부여 | AI에게 전문가 역할을 줌 | "너는 웹 디자이너야. 대학생 포트폴리오를 만들어 줘" |
| 예시 제공 | 원하는 형태를 보여 줌 | "프로젝트 카드는 '제목 / 기간 / 한 줄 설명' 형태로" |
| 단계 나누기 | 큰 작업을 작게 쪼갬 | "먼저 레이아웃만, 다음에 색상, 마지막에 애니메이션" |
| 제약 조건 | 꼭 지킬 조건 명시 | "외부 이미지 사용 금지, 파일 1개, 한글 UTF-8" |

> 막막할 때: **"내가 원하는 웹사이트를 만들기 위해 필요한 정보를 나에게 질문해 줘."** → AI가 질문하고 내가 답하면서 기획이 완성된다.

나쁜 예와 좋은 예:

```text
# 나쁜 예
홈페이지 만들어줘

# 좋은 예
영남대 컴퓨터공학과 2학년 학생의 자기소개 홈페이지를 만들어줘.
- 섹션: 소개, 관심 분야, 프로젝트(3개), 연락처
- index.html 파일 하나에 CSS와 JavaScript를 모두 포함
- 한글이 깨지지 않도록 UTF-8 설정
- 파란색 계열의 깔끔한 디자인, 모바일 화면에서도 보기 좋게
```

### 수정 요청은 구체적으로, 한 번에 하나씩

| 막연한 요청 | 구체적인 요청 |
| --- | --- |
| 더 예쁘게 해 줘 | 제목 글씨를 더 크게, 섹션 사이 여백을 넓게 해 줘 |
| 뭔가 추가해 줘 | 오른쪽 위에 다크모드 전환 버튼을 추가해 줘 |
| 이상해 | 모바일에서 프로젝트 카드가 겹쳐 보여. 한 줄에 하나씩 나오게 해 줘 |

반복 개선 예시(v1 → v3): 4요소 프롬프트로 v1 → "제목이 작고 섹션이 붙어 있다" → 여백·제목 크기 수정(v2) → "밤에 보기엔 눈이 부시다" → 다크모드 버튼 추가(v3).
매 단계 **하나만 바꾸고 바로 확인**하면 문제가 생겨도 원인을 쉽게 찾는다. 마음에 드는 버전은 코드를 따로 저장해 둔다.

### 오류가 났을 때 쓰는 프롬프트 패턴

| 상황 | 요청 예시 |
| --- | --- |
| 화면이 깨짐 | "모바일에서 카드가 겹쳐 보여. 원인을 설명하고 고친 전체 코드를 줘" |
| 버튼이 동작 안 함 | "다크모드 버튼을 눌러도 아무 변화가 없어. 무엇을 확인하면 될까?" |
| 이전이 더 좋았음 | "방금 수정은 취소하고 바로 전 버전으로 돌아가 줘" |
| 오류 메시지가 있음 | 오류 문구를 그대로 붙여넣고 "이 오류의 원인과 해결 방법을 알려 줘" |
| 너무 많이 바뀜 | "다른 부분은 그대로 두고 헤더 색상만 바꿔 줘" |

상황 전달의 핵심: **무엇을 했고 → 무엇을 기대했고 → 실제로 어떻게 됐는지**.

코드를 이해하는 질문 예: "부분별로 초보자도 이해하게 설명해 줘", "`<style>`에서 색상을 바꾸려면 어느 줄을?", "다크모드 버튼 원리를 3줄로", "개인정보나 보안상 문제가 될 부분이 있는지 확인해 줘".

### 배포 전 체크리스트

| 확인 항목 | 확인 방법 |
| --- | --- |
| 요청한 섹션이 모두 있다 | 미리 보기 화면 확인 |
| 한글이 깨지지 않는다 | `<meta charset="UTF-8">` 포함 여부 |
| 모바일에서도 보기 좋다 | 브라우저 창을 좁게 줄여 보기 |
| 버튼·기능이 동작한다 | 직접 클릭 |
| 개인정보가 없다 | 전화번호·주소·학번 등 삭제 |
| 외부 파일에 의존하지 않는다 | 파일 하나로 동작하는지 확인 |
| 코드 전체를 복사했다 | `<!DOCTYPE html>`로 시작해 `</html>`로 끝나는지 |

## 5. Part 4 — 네이버클라우드 웹서버로 배포

### 배포란

내 노트북에서 만든 파일을 서버로 옮겨 누구나 인터넷으로 볼 수 있게 하는 것.

```
[Claude가 만든 index.html] → 복사 → [내 노트북] → SSH 원격 접속 → [Ubuntu Server /var/www/html/index.html] → http://<공인 IP>
```

### 브라우저와 웹서버의 대화(HTTP)

① 사용자가 `http://<공인 IP>` 입력 → HTTP 요청(80번 포트) → ② ACG가 80번 허용 여부 확인 → ③ 웹서버(Nginx)가 `/var/www/html/`에서 `index.html`을 찾아 HTTP 응답 → ④ 브라우저가 HTML·CSS·JS를 해석해 화면 표시

- **클라이언트**: 요청하는 쪽(내 브라우저) / **서버**: 응답하는 쪽(NCP Ubuntu 서버)
- **HTTP**: 웹 페이지를 주고받는 약속(프로토콜), 기본 80번 포트
- 따라서 **서버의 `index.html`만 바꾸면 브라우저 화면이 바뀐다.**

### SSH — 서버를 원격으로 조작하는 통로

- **SSH(Secure Shell)**: 내 PC에서 멀리 있는 서버에 **암호화된 통로(22번 포트)**로 접속해 명령을 내리고 파일을 주고받는 방법
- 접속 정보 3가지: **주소(공인 IP) · 계정(root) · 비밀번호(root 비밀번호)**
- 파일 전송용 **SFTP**도 SSH 통로를 이용한다.
- SSH 비밀번호가 있으면 서버의 모든 것을 바꿀 수 있으므로 **절대 공유하거나 AI 채팅창에 입력하지 않는다.**

### 문서 루트

Ubuntu 웹서버의 기본 폴더(문서 루트)는 `/var/www/html`이고, 이 폴더의 `index.html`이 첫 화면이 된다. 오늘 할 일 = 이 파일을 내가 만든 파일로 교체.

### 원격 접속 방법: 목표는 하나, 길은 여러 개

| 방법 | 동작 방식 | 오늘 배포 방법 | 추천 대상 |
| --- | --- | --- | --- |
| **VS Code Remote SSH** | 접속하면 서버에 VS Code Server가 자동 설치되어 서버 파일을 내 PC 편집기처럼 열고 저장. 저장(Ctrl+S) 순간 서버 파일이 바뀜 | 서버의 `index.html`을 열어 코드 붙여넣기 → 저장 | 기본 방법(모든 OS) |
| **MobaXterm** | 터미널 + 왼쪽 SFTP 파일 탐색기. 같은 이름 파일은 덮어쓰기 | PC에 저장한 `index.html`을 드래그 앤 드롭 | VS Code가 안 될 때(Windows) |
| **터미널 ssh · scp** | 설치 없이 기본 제공, 명령으로 업로드 | PC에 저장한 `index.html`을 `scp`로 업로드 | VS Code가 안 될 때(Mac · Linux) |

어떤 방법이든 **`/var/www/html/index.html`이 바뀌면 성공**이다.

### 배포 전 확인할 3가지

1. 서버 공인 IP와 root 비밀번호를 알고 있는가?
2. ACG에서 22번(SSH), 80번(HTTP) 포트가 열려 있는가?
3. 웹서버가 실행 중인가? (어제 페이지가 브라우저에 보이는가?)

### 안전한 배포 3단계: 백업 → 교체 → 확인

| 단계 | 방법 |
| --- | --- |
| 1. 백업 | `cp index.html index_day1.html` (어제 파일 보관) |
| 2. 교체 | VS Code 붙여넣기·저장, 또는 MobaXterm 드래그, 또는 `scp` |
| 3. 확인 | `head -n 10 index.html` + 브라우저 강력 새로고침(Ctrl+F5 / Mac ⌘+Shift+R) |

- 문제가 생기면 `cp index_day1.html index.html` 한 줄로 복구
- 서버 파일 내용(터미널)과 실제 화면(브라우저)을 **둘 다** 확인
- 예전 화면이 보이면 브라우저 캐시 때문일 수 있으니 강력 새로고침

### "안 보여요!" 원인 찾기 지도

| 증상 | 의심할 곳 | 확인 방법 |
| --- | --- | --- |
| 사이트가 아예 안 열림 | ACG 80번 · 웹서버 정지 | 콘솔 ACG 규칙 · `systemctl status nginx` |
| 원격 접속 시간 초과 | ACG 22번 · 공인 IP 오타 | 콘솔 ACG 규칙 · 기록한 IP와 비교 |
| 예전 페이지가 그대로 | 저장 안 함 · 캐시 | Ctrl+S 확인 · Ctrl+F5 |
| 한글이 깨짐 | 인코딩 | `<meta charset="UTF-8">` · UTF-8 저장 |
| 화면이 하얗게 비어 있음 | 코드 일부만 복사 | `head` · `tail`로 파일 앞뒤 확인 |

> 문제를 **네트워크(ACG) → 서버(웹서버) → 파일(내용) → 브라우저(캐시)** 순서로 좁혀 가면 빠르다.

### 보안 기본 수칙

- 비밀번호, 인증키(`.pem`) 파일은 절대 다른 사람과 공유하지 않는다.
- 웹페이지에 전화번호·주소 같은 개인정보를 넣지 않는다.
- AI 채팅창에 서버 비밀번호를 입력하지 않는다.
- 실습이 끝나면 강사 안내에 따라 서버를 정지/반납한다.
